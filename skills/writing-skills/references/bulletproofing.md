# Clear Behavioral Boundaries

Use this reference when an important rule is repeatedly missed despite being relevant and authorized. First verify that the rule itself serves the user's task; stronger wording cannot repair a bad requirement.

## Express the decision precisely

State the condition, required outcome, and important limits together. Examples:

- If a reviewer is assigned the current working tree, include scoped staged, unstaged, and untracked changes.
- If a required action is already authorized in the session, continue without asking for the same approval again.
- If a check's relevant inputs changed, rerun affected validation before claiming the new state is verified.

Use explicit conditions for real exceptions. Avoid vague phrases such as “unless it matters,” but do not erase valid exceptions or replace user judgment with unconditional procedures.

## Diagnose before adding rules

A missing action may come from poor discovery, unavailable tools, incomplete context, an ambiguous instruction, or an unreasonable workflow. Address that cause. If a required output field is being omitted, improve the output structure. If examples conflict, reconcile them instead of adding another warning.

Validate significant changes with realistic outcomes and counterexamples. Preserve useful work when a check fails and make a focused correction; do not require deleting implementation or documentation as a penalty for process order.

Use firm language for actual safety, correctness, or authorization boundaries. Avoid guilt, invented urgency, fabricated authority, or treating all adaptation as rationalization. [persuasion-principles.md](persuasion-principles.md) explains this distinction.
